# 跨会话消息策略

实现位于独立工作区 `/Users/atou/agents-in-discord-task-submit`，分支 `feat/local-task-submit`。截至 2026-09-20，五个接收实例均已部署并完成重启核验；Codex 已通过 settings 完全放行、真实任务运行和用户续聊同一 session 的验收。其它接收方策略尚未配置，不能把入口上线说成跨 Agent 真实任务已经跑通。下方测试记录中的“尚未部署”保留为各轮测试当时状态。

## 本机初始配置

运维可在受信任的 `.env` 中设置 `LOCAL_TASK_INITIAL_POLICIES={"GUILD_ID":{"mode":"allow","ownerUserId":"USER_ID"}}`，也支持 provider 前缀。运行中的机器人重启后，在取得单实例锁并登录后经现有策略存储初始化尚未配置的服务器策略。owner 必须在该实例已有用户白名单中；配置不扩大频道或工作区权限，不从任务请求中接受归属身份。已有策略不覆盖，之后在 settings 中改为审批不会因重启再次放开。坏 JSON、非法模式或未授权 owner 会明确失败，不清空数据。

这是机器管理员的配置文件授权边界，不是将 CLI 自报用户身份视为 Discord 用户认证。外部进程不直接改会话数据库。配置允许与审批仍共用原有持久化、队列和权限检查。

## Discord 管理

设置面板入口：`/<prefix>_settings` → 分区选择“跨会话消息” → 接收策略“完全放行 / 需要我审批”。面板显示当前值、归属用户及全 Agent / 当前服务器作用域。尚未配置时不预选“完全放行”；未启用本机入口时显示不可用且不提供选择控件。面板与下述独立 slash 共用 `setPolicy`、真实交互身份检查和持久化，不另存 thread 级策略。

本次设置入口验证：`node --test test/settings-panel.test.mjs test/local-task-submission.test.mjs test/command-spec.test.mjs test/slash-command-router.test.mjs`，169 项通过。覆盖两种选择及回显、其他用户冒用面板、非法选项、后端权限拒绝、入口未启用、共用策略持久化。`node --check src/index.js`、`git diff --check` 均通过。尚未进行真实 Discord 设置面板点击验收；需要部署并空闲重启 Codex 后才生效。

每个接收方机器人使用自己的 `/<prefix>_agent-messages`。prefix 沿用实例现有 SLASH_PREFIX，不固定为模型名。

- `action:policy mode:allow`：完全放行后续请求，不再需要逐 thread 或逐请求授权。
- `action:policy mode:approval`：后续请求先进入审批，不创建目标 thread、不入队。来源 thread 收到提醒和完整 prompt 附件。
- `action:status`：查看策略、待审批数量及前 15 个请求 ID。完整请求仍可按 ID 查询。
- `action:show request-id:ID`：查看来源、目标、工作区方式及完整 prompt 附件。
- `action:approve request-id:ID` 或 `action:reject request-id:ID`：批准或拒绝该请求。

作用域是当前服务器内、当前接收方 Agent 的全部 thread，不是当前 thread。各 Agent 独立设置。修改策略不会自动批准旧的待审批请求；已经入队的工作仍由正常取消入口管理。策略在接收检查时生效，不撤销已经执行的副作用。

管理复用接收实例现有 `ALLOWED_USER_IDS` 显式用户白名单，同时检查现有频道允许规则。没有白名单配置时拒绝管理，不默认让所有 Discord 用户获得管理权限，也不授予项目升级或部署权限。策略归属为执行 slash 设置的真实用户；逐项批准后归属为批准用户。执行前重新检查其白名单资格及来源、目标 Discord 访问权限，排队、取消和重试沿用正常身份归属。

## Agent 使用

向已有 thread 提交任务，接收方已配置策略时不需要 authorization-message：

```sh
node scripts/submit-task.mjs \
  --socket /Users/atou/.aid-tasks/tasks.sock \
  --request-id jev-task-20260919-02 \
  --source-thread 1550810498470256691 \
  --target-thread 1550808791782785045 \
  --kind task --prompt-file /absolute/path/task.txt
```

`--kind notify` 只投递完整通知，绝不触发 runner；通知同样服从接收策略。新建任务用 `--parent CHANNEL_ID --title TITLE` 代替 `--target-thread`，默认隔离工作区。`--share-source` 仅允许接收实例可验证的来源工作区，仍走现有锁和工作区检查。已有 thread 继续目标 session，不复制来源上下文、模型设置或工作区。

查询：`node scripts/submit-task.mjs --socket PATH --request-id ID --status`。
请求超时后查询或重提同一个 ID，不能换 ID 掩盖不确定结果。相同 ID 相同内容返回原状态；内容或 kind 不同拒绝。

## 状态语义

- `accepted`：已持久化接收，尚未证明权限通过或入队。
- `approval_publishing`：正在发送审批通知；异常或重启后标为 interrupted，不盲目重发。
- `pending_approval`：完整请求已存储、审批提醒已发送，尚未入队。
- `approved`：真实 Discord 用户已批准，等待处理，不代表启动。
- `rejected`：已拒绝，终态。
- `creating` / `thread_created`：正在创建 / 已创建目标 thread，均不代表运行。
- `thread_bound`：已绑定已有 thread、session 和工作区。
- `publishing`：正在投递任务正文，不代表启动。
- `queued`：已进入现有任务队列，可能等待当前任务或工作区锁。
- `starting`：正在调用现有 runner；仅拿到 session ID 也不冒充启动确认。
- `started`：观察到真实 runner 启动或输出事件。某些 provider 的 session ID 要到后续元数据才可得。
- `succeeded` / `failed` / `cancelled`：任务完成 / 失败 / 被正常取消。
- `notified`：通知已投递，未触发任务。
- `interrupted`：重启或 Discord 请求结果不确定；保留错误和现场，不自动重放可能有副作用的操作。

pending_approval 重启后保持等待；approved 和确定已排队的记录重走现有队列；运行中记录不自动重放。查询保留历史、错误、thread 链接及可得的 session 标识。模型只返回会话的 lastObservedModel，没有观测就返回 null。

## 信任边界

入口仍是同 UID 可访问的 0700 目录、0600 Unix socket，无公开网络接口。CLI 不能传入用户身份或策略；策略只能由真实 Discord slash 交互修改。现有 bot 消息忽略保护不变，任务经进程内入口入队，不冒充用户消息。

本机同 UID 进程属于受信调用方，可以提交任意 prompt 和声明来源 thread。这不是单个 Agent 的密码学身份认证，也不验证自然语言里是否有授权。完全放行表示真实管理员授予该本机入口持续提交权，不意味着额外的文件、频道或 runner 权限。两个机器人间无需父子层级；发送方选择接收实例 socket，接收方独立执行其策略。

未配置新策略时保留旧的精确授权消息兼容路径；一旦配置审批策略，旧授权不能绕过审批。没有新策略、也没有有效旧授权的提交失败。不会从外部修改机器人会话数据库。

1. 核对生产工作区差异，合入本轮涉及的源文件、CLI 和测试，保留生产已有改动。不覆盖数据目录。

5. 获得真实测试授权后，执行无副作用 task，核对 started、session 元数据和 thread 内结果，再由用户续聊验证同一 session；另测 notify 不触发和审批前无运行。
