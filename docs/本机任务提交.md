本文保留首阶段的逐请求授权方案与当时交付记录。当前版本支持多 Agent 接收方策略，日常入口见 [跨会话消息策略](跨会话消息策略.md) 与 [跨 Agent 入口启用](跨Agent入口启用.md)。以下“未部署”等陈述仅指首阶段记录，不代表最新部署状态。

这是 Codex 实例的受控提交入口，不是新的 runner 或跨 Agent 调度平台。支持同一 Discord guild 中的文本父频道和 forum。普通持久 thread 会按 Discord 的规则归档，不是临时旁问，也不会复制来源会话历史或模型覆盖设置。

## 授权与信任边界

用户在已有普通任务 thread 中发送以下命令，一次授权一个请求 ID 和目标父频道：

```text
!task-authorize demo-20260919-01 1481970636342431775
```

机器人确认并返回授权消息 ID。CLI 使用该消息 ID，服务器重新读取 Discord 原始消息，核对真实非 bot/non-webhook 作者、请求 ID、目标频道及工作区模式。不能用 bot 消息或自报用户 ID 授权。命令不自动启动任务，Agent 随后提交完整 prompt；新 thread 不需要再发“开始”。

自然语言的“去做吧”不被机器宣称为已验证授权，需要上述明确命令。这项授权限定一项请求、目标父频道和是否共享工作区，**不绑定 prompt 的逐字内容**。授权用户仍需信任本机 Agent 提交的任务。删除或修改授权消息会使尚未派发的任务及重启恢复重新验证失败，不会自动取消已启动任务；已启动任务用正常取消命令处理。

入口只监听 Unix socket，不监听 TCP。socket 父目录必须属于机器人 UID、权限 0700，socket 为 0600，拒绝符号链接路径和不安全目录。它信任同一 OS 用户下的进程及 root，不是同 UID 的恶意 Agent 隔离机制。其他同 UID 进程能查询记录或使用真实授权消息；请求 ID 不是秘密令牌。CLI 不读取 Discord token、不写会话文件。

复用 `isAllowedUser`、`isAllowedChannel`、`resolveSecurityContext`、正常队列限制与 workspace 锁。另外核对用户能读写来源 thread，并能在目标父频道查看、发消息和创建公开 thread。私有来源 thread 要求实际成员关系。不会自动扩大频道白名单、Discord 权限或 runner 权限。

## Agent 使用

授权之后，准备 UTF-8 prompt 文件并执行以下命令；示例中的授权消息 ID 应替换为机器人确认的真实 ID：

```bash
node /Users/atou/agents-in-discord/scripts/submit-task.mjs \
  --socket /Users/atou/.aid-tasks/tasks.sock \
  --request-id demo-20260919-01 \
  --parent 1481970636342431775 \
  --source-thread 1550810498470256691 \
  --authorization-message 1234567890123456789 \
  --title '无副作用验证' \
  --prompt-file /absolute/path/任务提示.txt
```

```bash
node /Users/atou/agents-in-discord/scripts/submit-task.mjs \
  --socket /Users/atou/.aid-tasks/tasks.sock \
  --request-id demo-20260919-01 --status
```

默认隔离到 `WORKSPACE_ROOT/agent-tasks/<thread-id>`，不受全局默认工作区或子 thread 继承设置影响。不接受任意路径。显式共享需要用户命令末尾加 `share-source`，CLI 同时加 `--share-source`，仅允许来源会话现有且有效的工作区；不使用旁问的共享锁豁免，来源占锁时正常等待。

标题最多 100 个字符；prompt 最多 128 KiB UTF-8，空内容、非法编码或超限明确拒绝。首条 bot 消息保留完整任务内容及“由来源会话经用户授权发起”、来源授权消息链接。超过 Discord 消息长度时，完整 prompt 放在该首条消息的 `task-prompt.txt` 附件，传入队列的仍是完整正文，禁用自动提及。

CLI stdout 为 JSON，包含 `requestId`、`status`、`threadUrl`、`sessionId`、`ownerUserId`、`sourceUrl`、`workspaceDir`、`error`、`errorCode`、`httpStatus`、`timedOut` 和状态历史。`observedModel` 只来自匹配运行会话的 `lastObservedModel`，没有实测信息时是 null，不从默认配置推断。

退出码 0 表示提交或查询成功，不表示任务已经完成。HTTP 拒绝或查询到失败、取消、中断时退出码 1。连接失败、超时等只会报 `status: unknown`，不伪造 accepted。默认传输超时 10 秒，可用 `--timeout-ms` 设置 1..120000；超时后查询或重提**同一个 ID、相同内容**，不要换 ID 重试。

## 状态语义

| 状态 | 确切含义 |
| --- | --- |
| `accepted` | 请求及完整输入已由机器人持久化，尚未完成 Discord 授权核验或创建 thread。 |
| `creating` | 已记录即将调用 Discord 创建 thread，不能推断创建成功。 |
| `thread_created` | Discord thread ID 已持久化，但未证明入队或启动。 |
| `publishing` | 正在发布或取得首条任务消息。 |
| `queued` | 已进入真实 `channel-queue`，可能正在等待 workspace 锁。 |
| `starting` | 已获得锁、即将调用现有 runner；会话初始化时可能已取得 session ID，但尚未收到启动事件。 |
| `started` | 收到 Codex runner 的 `thread.started` 事件并持久化 session ID；不是 Discord thread 创建成功。长运行模式由实际 turn/started 通知转成该事件。 |
| `succeeded` | 原始任务成功返回，正常结果发送流程已完成。 |
| `failed` | 核验、准备、入队、runner 或结果发送失败；错误证据保留。runner 超时另有 `timedOut: true`。 |
| `cancelled` | 正常队列取消、移出队列或运行取消已处理。 |
| `interrupted` | 创建/发布的结果不确定，或重启时任务已经可能启动；不自动重放。 |

状态追踪的是首次提交的任务。用户之后在 thread 内使用普通消息、`!status`、`!c` 或现有 slash 命令，走原有续聊和取消流程。频道启用了 mention-only 时，后续消息仍须按原规则提及机器人。用户手动 retry/new 是新的明确操作，不改变原请求的终态。

## 幂等与恢复

记录放在现有 provider 对应会话 DB 的 `localTaskRequests` 中，使用现有原子替换及 fsync 持久化。仅机器人进程写入。相同 ID、相同规范化输入只返回记录；相同 ID 不同标题、prompt、来源、授权消息或工作区模式返回 409，不创建或重跑。两个并发调用先同步持久化同一 ID，再进行异步工作。

重启后，`accepted`、`thread_created`、`queued` 重新验证授权及工作区并通过原队列恢复；已记录 thread ID 时不再创建 thread。`creating`、`publishing`、`starting`、`started` 转为 `interrupted`，保留原状态历史和已有链接，不猜测结果、不清空现场。损坏记录、指纹不符或缺少必要状态证据会阻止加载，不能偷偷当成新任务。

Discord 创建和首条消息发送使用同一 bot 身份及现有 REST 配置，但单独禁用该写入路径的底层网络/5xx 自动重试，不改变普通机器人请求策略。Discord 操作等待上限 30 秒；超时可能留下远端已创建但本地未知的 thread。此时人工结合请求 ID、Discord thread、日志和 session 检查后决定续聊，不能用新 ID 自动补跑。协议优先避免重复副作用，不声称跨 Discord/本地 DB 的 exactly-once 事务。

## 启用步骤

以下涉及运行目录及配置，**本次没有执行，需获得明确授权**：

1. 将开发工作区的本地改动整合到 `/Users/atou/agents-in-discord`。运行目录已有未提交修改，尤其 `src/index.js` 和 `.env.example`，必须保留并逐项整合，不能直接覆盖或 reset。没有新增依赖。
2. 在 Codex 实例配置中加入 `CODEX__LOCAL_TASK_SOCKET_DIR=/Users/atou/.aid-tasks`。该目录不存在时机器人会以 0700 创建；已存在但权限不安全会拒绝启动入口，不擅自 chmod 修复。不同机器人实例不能共用同一个 socket。
3. 确认 Codex 实例没有运行中及排队任务，再执行现有脚本 `scripts/restart-discord-bot-service.sh codex`。重启会中断该实例在途任务，不需要重启其他 provider。不得同时从开发工作区登录同一生产 bot。
4. 确认日志显示 `Local task submission socket: /Users/atou/.aid-tasks/tasks.sock`。用户在来源 thread 发明确授权命令后，Agent 才提交测试任务。已有白名单及 bot 权限不足时先报告，不自动修改。
5. 经授权进行真实验收：prompt 只要求“回复 LOCAL_TASK_OK，不运行工具、不写文件”；记录 accepted、thread 链接、实际 started/session ID、thread 内结果，然后用户发送“只回复 FOLLOWUP_OK”，确认仍是同一 session。补测正常取消。不能仅以 thread 创建成功判定通过。

停用时先处理在途请求，再移除该实例的配置并重启；保留 DB 中的请求历史。不要删除 socket、会话 DB 或 workspace 来绕过异常。
